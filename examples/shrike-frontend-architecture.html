Shrike Frontend Architecture

Seven browser apps sit on seven shared libraries. Nearly everything the user sees is a MobX-observable model fetched by one generic collection layer — so the interesting architecture is not the component tree, it is the path a request takes and the contract that makes a component re-render when the answer arrives.

§1The shape of the repo

Shrike is a Yarn 4 workspaces monorepo orchestrated by Turborepo. Dependencies run strictly downward: an app may reach into any library, a library never reaches back into an app, and no two libraries on the same layer depend on each other. Apps import libraries from their built dist/, not from source — which is why a first checkout needs yarn build:library, and why editing a shared component during development requires yarn watch to be running.

Its internal layout is conventional — src/App/ holds pages and route definitions, src/components/ holds 123 app-specific components, src/hooks/ holds 47 hooks, and src/state/ holds the contexts and store re-exports that everything else imports through the @feathr/extender/state alias.

§2The data path: one collection layer for every resource

No component fetches. A component asks a collection for a list or a model, gets back an object that is already observable and already knows whether it is pending, and renders it. The collection deduplicates the request by URL, so several components asking the same question in the same render produce one network call and share one result.

What a blackbox model actually is

Each API resource contributes three exports: an IResource interface describing the attributes, a Resource class extending Model, and a Resources class extending Collection. The model carries its own validation rules in a constraints getter, so the same rule drives the form input's error text, the submit button's disabled state, and the pre-save check.

Campaigns and targetables add a discriminated union on top: a _cls attribute selects the concrete subclass, and a disambiguateCampaign() factory returns the right one — 44 campaign classes descend from a shared base through per-channel intermediates.

Consequence

Because the models are real classes with real validation, tests instantiate them directly (new Campaign({ … })) instead of mocking them. A hand-rolled mock whose isValid() always returns true passes tests the real constraint would fail — which is why mocking blackbox models is banned outright in this repo.

§3Writes, and the failure that doesn't throw

Writes go through the same collection. model.set() mutates observable attributes and records the previous value in a shadow copy, which is what makes isDirty and rollback possible; patchDirty() then sends only the changed keys. The part that surprises everyone is the failure path.

§4The reactivity contract

Three rules hold the whole MobX layer together, and each of them fails silently when broken — no exception, no warning, just a component that shows stale data.

observer()

A component that reads model.get(), model.isPending, or collection.list() must be wrapped in observer from mobx-react-lite. Without it, the first render is correct and no render ever follows.

get / set only

Read through model.get(key) and write through model.set({ … }). Assigning to an attribute directly skips the observable, the dirty tracking, and the shadow copy that rollback depends on.

get() never returns undefined

Collection.get(unknownId) creates and returns a placeholder model rather than undefined. Absence has to be detected from the model's own state, not from a null check.

Two smaller edges follow from the same design. Models created through Collection.create() are marked ephemeral until saved, and helper code branches on that flag — an unsaved row gets spliced out of an array where a saved one gets archived through the API. And every model holds a reference back to its collection, which holds a map containing the model, so any attempt to serialize one produces a circular structure.

§5Two stores, one set of report cards

A Feathr report can be read two ways: by a logged-in user inside extender, or by a donor or board member opening a public share link. Both render the same card components, so the difference is pushed entirely into which store is above them.

Identity, permission, and account scope

Above the store sits a small set of hooks that every page depends on. They are the reason a page rarely has to think about the current account: the account id lives in the URL, and these hooks read it.

Hook Answers Notes
useStore() Which collections do I have? Returns the store instance from context; throws outside a provider.
useAccount() Which account am I in? Resolved from the :accountId URL segment. Ephemeral on first render.
useUser() Who is signed in? Also carries per-user settings such as dark mode and dev-nav visibility.
useFlags() Is this feature on? 38 flags, merged account-then-user, kept in sync by a MobX reaction.
useRole() May this user do it? Derives can* / has* flags from the user's role model plus license.
useLocalUrl() What is the link for this page? Prefixes any internal path with the current account id; leaves external URLs alone.
useActionBar() What buttons belong at the bottom? Page-level save / cancel actions, rendered by the layout rather than the page.
useNavigation() What state is the sidebar in? Minimized state and active secondary nav; persisted to localStorage.

§6Boot, providers, and the gates on a route

Extender's startup is a short chain with one hard stop at the front and a stack of soft gates at the back. Nothing renders until there is a session; once there is, the route table itself changes shape according to licence, role, flags, and onboarding progress.

Failure mode worth knowing

Because the account is fetched rather than embedded, a deep link can arrive before the store has hydrated it — the route resolves against an account that is still pending and 404s. Warming a known-good page first, then navigating in-app, is the usual workaround when this bites in tests or automation.

§7The UI layer

Presentation is deliberately narrow: app code composes @feathr/components and Mantine layout primitives, and reaches for a raw HTML element almost never. The library carries the design decisions so pages don't re-litigate them.

Inputs bind to models, not to state

Every form control ships in two shapes. The value shape is the familiar controlled input with value and onChange. The model shape takes model and attribute and writes straight through to the observable model — which is why components has to depend on rachis. Validation errors come from the model's own constraints, and FormSubmit gates its button on model.isValid(), so a form generally holds no local state at all.

Three layers of colour, one 4px grid

Styling is CSS Modules over CSS custom properties, with tokens layered so that intent stays visible: a global ramp (--color-cyan-700) exists only to be pointed at by semantic tokens (--color-action, --color-bg-success-primary), which are what feature code uses; component-scoped tokens stay inside the library. Spacing is a strict multiple of four, enforced by lint. The 2025 “Midnight” rebrand put deep navy on primary actions with cyan for links and focus, and violet reserved for recommendation surfaces so machine suggestions never look like the user's own choices.

Copy is data

Translation keys are the English strings themselves — t('Save changes') — so there is no key catalogue to keep in sync and no indirection when reading a component. Keys are extracted into /locales/*.json by a script. Casing carries meaning: title case for page and section headings, sentence case for labels, buttons, and everything else a person reads mid-task.

§8Build and delivery

Turborepo runs the graph; each app has its own Webpack 5 config layered over a shared base. The base config is where the frontend learns about the outside world: backend URLs, third party keys, and the CDN path are all resolved from SHRIKE_ENV at build time and compiled in as globals, so there is no runtime configuration fetch.

Backends, per environment

BLACKBOX_URL is the main API. Three siblings sit beside it: a short-link service, a preview/render service for creatives, and an asset CDN. Local development points them at local.feathr.app.

Assets are commit-addressed

publicPath embeds the build's short SHA, taken from CI's commit variable so the URL and the S3 upload path cannot disagree. Deploys ship a ref, not a build artifact.

Previews per pull request

CI on GitHub Actions builds a Scout preview for each PR and posts its link back on the pull request, alongside lint, type check, test, and Sonar results.

Parallel worktrees

Dev-server ports are offset by a hash of the worktree directory name, so several branches can run at once. Only the main checkout uses the base ports.

Libraries are built, not aliased: yarn build:library compiles the seven shared packages to dist/, and yarn watch keeps components and report_components rebuilding during development. Turbo caches those outputs — and because a worktree shares the primary checkout's cache, a stale entry can hand you a dist/ that does not match your source. When the browser disagrees with the code, check what is actually in the served bundle before believing either one.

§9Quality gates

Roughly one file in six is a test. Jest runs one project per package, and the shared setup in @feathr/testing applies to all of them without any test opting in — which makes a few of its choices worth knowing before debugging a failure.

  • A console.error fails the test. Unhandled MSW requests are reported that way too, so “unhandled GET” means a missing handler, not a flaky network.
  • Timers are partially faked. Date and requestAnimationFrame are faked while setTimeout stays real — so a Mantine transition needs the fake clock advanced, and a debounce needs it turned off.
  • CI retries twice, locally never. A green CI run is not proof a flake is fixed; a local failure is real.
  • Async work can outlive its suite. An unawaited write settles during an unrelated test and fails that one instead — the reporting test is the victim, not the cause.

Beyond Jest: ESLint carries repo-specific rules that encode the conventions above (no mocked i18n, no module-level store, no any in tests), Stylelint guards the CSS, Storybook plus Chromatic cover the component library visually, and a contract gate checks that no data-name attribute relied on by the Playwright end-to-end suite in the sibling repo has been deleted — a cross-repo break that would otherwise only surface after merge.
